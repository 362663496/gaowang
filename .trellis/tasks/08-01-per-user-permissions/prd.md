# 按用户管理权限

## Goal

让管理员在权限管理页按具体员工账号授予和撤销业务权限，不再让所有 `staff` 账号共享同一套权限。

## Background

- 当前 `apps/web/src/app/(app)/permissions/page.tsx` 只有一列“员工”权限，读写 `/api/v1/permissions` 的全局 `staff_permissions`。
- 后端 `EffectivePermissions` 对所有 `staff` 读取同一张 `staff_permissions` 表；管理员始终拥有完整权限目录。
- 权限依赖闭包、管理员专属权限校验、后端路由鉴权和审计机制已经存在，应继续复用。
- 这是数据库、Go API 和 Next.js 页面共同变更的跨层任务。

## Requirements

### R1. 用户级授权

- 每条员工权限必须归属一个具体用户；一个员工的修改不得影响其他员工。
- 新建 `staff` 账号默认零业务权限，由管理员按需授予。
- 管理员继续自动拥有全部权限，不进入可编辑授权范围。
- 只允许给 `staff` 用户写入可分配权限；未知权限和管理员专属权限继续被拒绝。
- 授权时继续自动补齐依赖；撤销基础权限时，页面继续同步撤销依赖它的权限。

### R2. 权限管理页面

- 页面展示员工身份信息，并允许切换当前编辑的员工。
- 权限矩阵只编辑当前员工，保存按钮和成功/错误反馈沿用现有 Ant Design 模式。
- 无员工、加载失败、保存中和只读状态均有明确反馈；表格在窄屏保持横向滚动。
- 默认采用单个员工选择器，不增加多列动态矩阵或批量授权。

### R3. 数据兼容

- 升级时将现有共享员工权限一次性复制给每个已有 `staff` 用户，避免现有账号失权。
- 迁移必须可重试，且后续重启不得覆盖已经完成的用户级调整。
- 保留旧共享授权数据以支持应用版本回滚；新代码只读取用户级权限。

### R4. 审计与访问边界

- 每次更新记录目标用户 ID、更新前权限和更新后权限。
- `/auth/me`、`RequireAuth` 和 `RequirePermission` 必须按当前登录用户读取有效权限。
- 权限查看和更新入口继续分别要求 `permission.read` 与 `permission.update`。

## Acceptance Criteria

- [x] AC1：管理员可选择任一员工并保存其权限，刷新页面后结果保持。
- [x] AC2：修改员工 A 后，员工 B 的权限完全不变；两人的 `/auth/me` 和业务路由鉴权结果各自正确。
- [x] AC3：管理员仍拥有完整权限，管理员账号不出现在可编辑员工列表中。
- [x] AC4：权限依赖闭包、撤销联动、未知权限和管理员专属权限校验保持有效。
- [x] AC5：旧共享权限只在首次升级时复制给已有员工；重复迁移或重启不覆盖后续个性化结果。
- [x] AC6：权限更新审计记录包含目标用户、`before` 和 `after`，写入与授权变更保持同一事务。
- [x] AC7：页面覆盖无员工、加载错误、保存错误、保存中及无更新权限状态。
- [x] AC8：Go 格式化、测试、静态检查，以及 Web lint、类型检查、测试和构建全部通过。

## Out of Scope

- 自定义角色、权限组、部门继承或权限模板。
- 批量复制、导入导出或多用户同时编辑。
- 改变管理员全权限规则或允许员工管理权限。
